# realtyprice 기능명세서

이 문서는 "이 화면에 뜨는 이 숫자가 대체 어디서 온 거냐"를 바로 찾기 위한 문서다.
모든 항목을 **자료출처(어느 외부 API의 어느 필드인지, 아니면 자체 계산인지) 수준까지** 적는다.
추측·설계의도가 아니라 실제 코드(2026-07 기준)를 그대로 옮겼다.

관련 문서: 가중치를 왜 그렇게 잡았는지의 "설계 근거"는 `docs/price-model-research.md` 참고.
이 문서는 "지금 코드가 실제로 뭘 하는지"만 다룬다.

---

## 1. 전체 사용 흐름 (파이프라인)

```
① 대상아파트 검색           한국부동산원 odcloud (getAptInfo)
      ↓ 저장
② 상세정보 표출             국토부 K-apt(완공단지) + 청약홈(분양단지) + 학구도(로컬 JSON)
      ↓
③ 비교단지 자동추천         한국부동산원 odcloud + VWorld 지오코딩 + 학구도
   + 대장아파트 설정         하드코딩 테이블(leaderApartments.ts) + 실거래 비율 자동산출
      ↓ 저장 (comparableApartments, comparableRules)
④ 실거래·호가 수집          국토부 실거래 + 직방(비공식) + KB부동산(비공식)
      ↓ 저장 (transactions, listings)
⑤ 가격추정 실행             priceModel.ts — 11개 가격신호 + 5개 상승신호를 가중합산
      ↓
⑥ 결과 표시                 예상매매가 / 권장호가 / 상승가능성 점수 / 근거·경고 문구
```

각 단계는 `src/app/targets/[id]/page.tsx`의 3단계 위저드(`dataStage` 1/2/3)로 묶여있다.
①②는 `dataStage=1`, ③은 `dataStage=2`, ④는 `dataStage=3`, ⑤⑥은 `tab="analysis"`.

## 3. 가격추정 엔진 (`src/lib/priceModel.ts`) — 11개 가격신호

기본 가중치(합 100%, `src/lib/seed.ts`의 `defaultModelWeights`) 및 계산식:

| # | 컴포넌트 | 기본 가중치 | 계산식 | 데이터 출처 |
|---|---|---|---|---|
| 1 | 대상단지 실거래가 (`targetSalePrice`) | **20%** | 대상단지 매매·분양권 실거래를 시간감쇠·면적적합도로 가중평균, 선택평형 기준 ㎡당가 환산 | 국토부 실거래 (대상단지만) |
| 2 | 비교단지 보정 실거래가 (`adjustedComparableSalePrice`) | **23%** ⚠️ | 비교단지 실거래를 상·하급지 보정(`comparableLocationAdjustments`, ±12%)·비교단지가중치·시간감쇠로 가중평균 | 국토부 실거래 (비교단지) |
| 3 | 비교단지 현재 호가 (`comparableAskingPrice`) | 10% | 비교단지 매물 호가 중앙값, 상·하급지 보정 적용 | 직방·KB 호가 (비교단지) |
| 4 | 대상단지 현재 호가 (`saleAskingPrice`) | 12% | 대상단지 매물 호가 중앙값 | 직방·KB 호가 (대상단지) |
| 5 | 전세기반 하방가 (`jeonseFloorPrice`) | 10% | (전세 실거래+호가 평균) ÷ 전세가율. 전세가율은 최근 실거래 매매/전세 중앙값 비율(0.40~0.85 클램프), 없으면 기본 0.65 | 국토부 전세 실거래 + 직방/KB 전세호가. 월세 실거래는 `convertMonthlyRentToJeonse()`로 환산전세가 변환(전월세전환율 고정 5%) 후 합류 |
| 6 | 매물 회전속도 반영가 (`inventorySignalPriceEffect`) | 8% | 가격앵커 × MOI(재고소진월수) 구간별 배율(0.98~1.05) | MOI = 활성매물(직방/KB) ÷ 월평균 실거래건수(국토부, 최근 6개월) |
| 7 | 분양가 프리미엄 (`presalePremiumPrice`) | 5% | 청약홈 분양가 × (실거래/분양가 비율, 0.90~1.30 클램프) | 청약홈 분양가 + 실거래 |
| 8 | 매크로 신호 (`macroSignalPrice`) | 3% | KB 매수우위지수·가격전망지수 결합(100기준 편차) × 호가/예상가 앵커, ±5% 클램프 | KB부동산 매크로 지수 (실패시 0 → 이 컴포넌트 제외) |
| 9 | 대장아파트 앵커 (`leaderApartmentAnchorPrice`) | 5% | 대장 실거래 가중평균 × 대상/대장 비율(`targetToLeaderRatio`) | 대장 실거래(국토부) + `autoLeaderRatio()` |
| 10 | 대상 입지 보정 (`locationPremiumPrice`) | 2% | 앵커가격 × (1+입지보정률, ±8% 클램프) | Overpass(OSM) 지하철/마트/공원 거리(`location-score` API) + 주소 텍스트 키워드 폴백 |
| 11 | 비교단지 상·하급지 압력 (`comparableMarketPressurePrice`) | 2% | 앵커가격 × (1+압력률, ±5% 클램프) | 비교단지들의 `locationQualityScore` 대비 대상 점수차 평균 |

⚠️ **CLAUDE.md에 적힌 "비교단지 보정 실거래가 25%"는 오기(誤記)** — 실제 코드
(`src/lib/seed.ts`)는 **23%**다. 합계가 100%가 되려면 23%가 맞음(20+23+10+12+10+8+5+3+5+2+2=100).

활성화된(값>0이고 가중치>0인) 컴포넌트만 가중평균해 `expectedSaleMid`를 산출.
최소~최대는 ±3%.

### 3-1. 지역 레짐 보정

`regionProfileFromAddress(address)` — 주소 앞글자가 "서울"이면 seoul, "경기"/"인천"이면
gyeonggi, 그 외 default. 프로파일별로 위 가중치에 배수(`REGION_WEIGHT_MULTIPLIERS`)를
곱한 뒤 원래 합계로 재정규화. 예: 서울은 비교단지압력×1.7·대장앵커×1.6, 경기는
비교단지압력×1.5·분양가프리미엄×1.4. (실증 계수 아닌 리서치 기반 prior — 코드 주석에 명시)

### 3-2. 공급절벽 모드 (수동 토글)

향후 2년 공급량이 부족하다고 판단될 때 사용자가 켜는 옵션. `SUPPLY_CLIFF_MULTIPLIERS`로
입지비중↓(×0.35), 전세소진·호가lock-in↑(×1.6~1.7)로 재조정. 데이터 출처는 위와 동일,
가중치 배수만 다르게 적용.

## 4. 상승가능성 점수 (0~100, `upsideScore`) — 기저값 + 5개 신호

| 항목 | 배점 | 계산 근거 | 데이터 출처 |
|---|---|---|---|
| 기저값 | +35 (고정) | 데이터 존재 시 중립 출발점 | — |
| 거래 속도(velocity) | 최대 +20 | 최근 2주/1개월 거래량을 3개월 기준선 대비 가속도로 환산. 대장(1.8배)>대상(1.2배)>비교단지(≤1.0배, `comparableWeights` 가중) | 국토부 실거래 계약일 (신고지연 보정: 최근 14일은 2배 보정) |
| MOI 수급 타이트니스 | -6~+8 | 재고소진월수 구간표 (<2개월=+8 ~ >9개월=-6) | 직방/KB 활성매물 ÷ 국토부 월평균 실거래 |
| 전세 수요/공급 | -4~+7 | 전세가율 구간표 (≥70%=+7 ~ <50%=-4) | 국토부 전세실거래 ÷ 매매실거래 |
| 대장 앵커 상방압력 | 0/+6 | 대장 환산가가 비교단지 시세보다 높으면 +6 | 대장 실거래 + `targetToLeaderRatio` |
| 비교단지 상·하급지 압력 | -3~+6 | `comparableMarketPressureRate`(3-11번과 동일 산식) × 120(상급) 또는 ×60(하급) | 3-11번과 동일 |
| 입주물량 공급압력 | -8~+6 | 국토부 3개월 합산 입주예정 세대 구간표 | `supply-volume` API |

합산 후 0~100 클램핑. 데이터가 전혀 없으면(`hasMinData=false`) 0점 처리하고
`conclusion="insufficient_data"`.

## 5. 대장아파트 판별 로직 상세

```
isLeaderByComplexPk(complexPk)          // ① 정확매칭 — complexPk 완전일치
  → true면 대장 확정
isLeaderApartment(name, address, pk)     // ② 폴백 — 이름+지역 퍼지매칭
  → 지역(region) 키워드로 1차 게이팅 후 이름 4자 이상 부분포함 매칭
findLeaderForAddress(address)            // ③ 대상 주소로 지역 대장 자동 추천
  → region 문자열 길이 긴 순으로 정렬해 가장 세분화된 매칭 우선
```

전부 `src/lib/leaderApartments.ts`. 48개 항목 각각 `region`(매칭키워드)·`name`·`address`·
`brand`·`households`·`complexPk`를 가진다. **complexPk가 비어있는 항목은 이름매칭 폴백만
가능해 오매칭 위험이 있음** — `households` 있는 항목은 대부분 검증됨, 일부(평택지제역자이
등)는 `households` 없이 등록되어 있어 재검증 필요.

## 6. 상태관리 아키텍처 (`src/lib/clientStore.ts`)

- **저장소**: Vercel Postgres 우선(`/api/db/[entity]`), 실패 시 `localStorage` 폴백
- **캐싱**: 모듈 레벨 `_state` 싱글톤, TTL 5분. `useSyncExternalStore`로 모든 컴포넌트가
  같은 `_state`를 구독 — 한 컴포넌트에서 저장하면 같은 화면의 다른 컴포넌트도 즉시
  갱신됨 (2026-07 수정 전에는 컴포넌트마다 독립 state라 동기화 안 되는 버그가 있었음)
- **엔티티 7종**: apartments, comparableRules, comparableApartments, transactions,
  listings, inventorySignals, priceEstimates
- **API 키**: `localStorage`에만 저장(`STORAGE_KEYS.apiKeys`) — 서버로 전송하지 않고
  요청 시마다 클라이언트가 쿼리파라미터로 붙여서 호출. 단, `HUG_API_KEY`는 예외로
  Vercel 환경변수에 서버측 저장(`.env.local` / Vercel 대시보드)

## 8. 알려진 이슈 (2026-07 기준)

1. **직방(Zigbang) 수집이 대부분 실패** — 완공된 실제 단지(대장아파트 등)까지 실패하는
   걸로 봐서 서버(Vercel) IP 자체가 차단됐을 가능성이 높음. **`/admin/diagnostics` 페이지에
   이미 서버측에서 직방·KB를 직접 호출해보는 진단 항목이 있다** — 배포된 사이트에서 이
   페이지를 열면 브라우저 Network 탭 없이도 "직방 API" 항목의 상태(ok/warn/error)와
   HTTP 코드로 바로 원인이 서버 차단인지 아닌지 확인 가능.
2. **HUG 분양가 트렌드 API** — 라우트(`/api/hug-presale-trend`)만 만들어져 있고
   `priceModel.ts`의 실제 가격/상승신호로는 아직 연동 안 됨.
3. **CLAUDE.md의 가중치 표기 오류** — "비교단지 보정 실거래가 25%"는 실제 코드(23%)와
   다름. 문서만 안 고쳐진 상태.
4. **대장아파트 48개 중 일부는 재검증 필요** — `complexPk` 없이 이름매칭 폴백만 있는
   항목(예: 평택지제역자이)은 오매칭 위험. `/admin/verify-leaders`로 주기적 재확인 필요.
5. **직방/KB 모두 비공식 API** — 공식 문서가 없어 언제든 응답 스키마가 바뀔 수 있음.
   현재 파싱 로직은 관측된 응답 구조에 기반한 역공학 결과.
